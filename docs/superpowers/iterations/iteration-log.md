- **Live proof-run against a real account** (credentials in `.dev-secrets/`, gitignored), across two sessions with a pause in between per explicit user direction to avoid over-hammering the account:
  1. First pass found and fixed a real bug: `TrustSession`/2FA calls used the narrower SMS-only OAuth header set instead of the reference client's full `_get_auth_headers()` set, and `scnt`/session_id weren't carried from signin/init into signin/complete's headers.
  2. Second pass (after a rate-limit-suspected `-20101` error cleared overnight) found the actual root cause of a persistent CloudKit 401 `AUTHENTICATION_FAILED`/"no auth method found": the `Session` struct was only ever populated once from signin/complete's headers, never updated from later responses (SMS verify, `/2sv/trust`, accountLogin) — so `accountLogin` was sent a stale, pre-2FA trust token even after 2FA nominally succeeded. Fixed by merging session-relevant headers from every 2FA-related response, matching the reference client's `session_data` accumulation behavior. Confirmed live: `hsaTrustedBrowser` flipped from `false` to `true`, and CloudKit calls (`zones/list`, `records/query`) started succeeding.
  3. That surfaced STORY-0019's checksum-format assumption was wrong: a live `fileChecksum` decoded to 21 bytes, not the guessed 33 (1 version byte + SHA-256). Investigation found the true value is 20 bytes (matching SHA-1 length) but does NOT match SHA-1 of the downloaded bytes either. Structural analysis showed the CPLMaster recordName is literally `0x01 || fileChecksum` — confirming the field is Apple's MMCS content-addressable hash (chunked, aggregated), not a plain digest. Independently confirmed via `steilerDev/icloud-photos-sync` (a mature, actively-maintained TypeScript iCloud Photos client): its `asset.ts` has an unused, commented-out `verifyChecksum` method whose comment reads *"This is currently NOT implemented, as the checksum algorithm is unknown"* — its dead code brute-forced every standard hash (MD5, SHA1, SHA224/256/384/512, SHA3 family, BLAKE2, SM3) across multiple encodings plus HMAC-keyed variants, with no match. Per explicit user direction, narrowed STORY-0019 to a size check rather than continuing to chase an algorithm a more mature project already gave up on.
  4. With that fixed, the full journey ran clean — but filenames on disk were garbled base64 strings. Found the cause: `filenameEnc` can be type STRING or ENCRYPTED_BYTES, and the code always treated it as a plain string. Fixed to check the type and base64-decode when needed (matching `PhotoAsset.calculate_filename` in the reference client). Re-ran live to confirm: real filenames (`IMG_0047.HEIC`, `Cat.jpg`, etc.).
  5. Final live run: 20 assets downloaded with correct names and sizes, 20 manifest rows recorded, process exited 0. JOURNEY-0001 closed.
